# Android Care

Локальная диагностика Android **без обязательной настройки Shizuku**. Дополнительные действия доступны при уже настроенном shell-доступе через Shizuku / rish или ADB. Старый Android/web-проект заменён этим набором скриптов.

**Не «волшебный ускоритель».** Скрипт не проверяет всё оборудование и не исправляет износ железа; Shizuku не открывает все закрытые данные приложений. Скрипт показывает доступные показатели, отмечает недоступные разделы и не выдаёт отсутствие ошибок за гарантию исправности.

## Одна команда в Termux — без ZIP и ручного копирования

Для **первой установки** вставьте одну строку в Termux:

```sh
pkg install -y git && git clone --depth 1 --single-branch --branch arena/3e57b85e-calculator https://github.com/jarganaterow-ctrl/Calculator.git "$HOME/Android-Care" && sh "$HOME/Android-Care/run.sh"
```

Репозиторий теперь **публичный**: GitHub CLI, вход, токены и ручное скачивание ZIP не нужны. Команда устанавливает `git` штатным пакетным менеджером Termux, клонирует текущую рабочую ветку и запускает read-only проверку. Если клонирование не удалось, выполнение скрипта не продолжается.

Для уже установленной через git версии — обновление и меню одной строкой:

```sh
git -C "$HOME/Android-Care" pull --ff-only && sh "$HOME/Android-Care/run.sh" menu
```

Папка `$HOME/Android-Care` должна ещё не существовать: команда не стирает и не перезаписывает старую установку. Если уже клонировали именно эту ветку, повторный запуск — `sh "$HOME/Android-Care/run.sh"`. Для обновления такой установки: `git -C "$HOME/Android-Care" pull --ff-only` (локальные изменения могут потребовать ручного решения). Если папка от прежнего ZIP, используйте другое имя для нового клона; не удаляйте свои файлы автоматически.

### Как выбирается режим

| Что уже есть | Что произойдёт |
| --- | --- |
| Только Termux, без Shizuku/rish | **Базовая диагностика** доступных Android показателей. Без изменения системы; закрытые разделы честно отмечаются как непроверенные. Отчёт: `$HOME/.android-care/report-*`. |
| Настроенный `rish` в PATH, в папке `rish/` проекта или по переменной `RISH` | Полная диагностика через Shizuku; изменения доступны отдельными действиями после подтверждения. |
| Терминал уже работает с UID 2000 или 0 | Прямой запуск полного режима без второй прослойки rish. Root не запрашивается. |

Если rish найден, но диагностика через него завершилась с ошибкой, стандартный запуск переходит к локальной диагностике. **Изменяющие действия и меню автоматически не повторяются:** первое действие уже могло частично выполниться. Ошибочный явно заданный путь `RISH` не игнорируется.

Без shell-доступа скрипт **не может** менять системные настройки, очищать чужие кэши или читать защищённые `dumpsys`. Это ограничение Android, а не дополнительный шаг установщика. Root, отключение SELinux и обход разрешений не предлагаются. Даже часть `/proc` и `/sys` может быть закрыта прошивкой.

### Про «300 FPS»

Обещаний «300+ FPS на любом телефоне» здесь нет. FPS зависит от игры, её лимитов, нагрузки, CPU/GPU, охлаждения и настроек. Чтобы видеть 300 отдельных кадров в секунду, нужен и соответствующий дисплей. Частота экрана в Гц — **не замер FPS игры**. В полном режиме отчёт показывает доступные поля режимов дисплея, если прошивка их публикует, но не форсирует неподдерживаемые частоты и не подменяет устройство для обхода игровых ограничений.

Анимации 0.5x сокращают длительность переходов интерфейса, а не ускоряют отрисовку игры. Цель инструмента — увидеть ограничения, не навредить системе и дать обратимые настройки, а не показать фиктивный прирост.

## Что внутри

- Запуск одной командой с автоматическим выбором базового/полного режима. В полном режиме: модель/версия/патч безопасности, CPU, память и PSI, накопитель, батарея, доступные температуры и частоты CPU, режимы дисплея, Doze, несколько настроек и количество пакетов. В базовом — только доступные без shell показатели.
- Текстовый отчёт и краткая оценка доступной ОЗУ, свободного места и температуры батареи. Есть пояснения, а не выдуманный «балл здоровья».
- Штатный **игровой performance-режим** только для поддерживаемой игры, с проверкой температуры, снимком исходного режима и откатом. Никакого принудительного создания интервенций.
- **HWUI-статистика** приложения: jank и процентили времени кадров, без выдачи их за FPS игрового движка.
- **CSV-мониторинг** нагрузки CPU, доступной ОЗУ, температуры батареи и thermal status во времени. Недоступные величины — `NA`.
- Ускорение **анимаций интерфейса до не более 0.5x**, только после подтверждения; точные исходные значения сохраняются для отката. Если параметр изначально отсутствовал, при откате он удаляется, а не заменяется на произвольное значение.
- Отдельный запрос Android на очистку восстанавливаемого кэша — тоже только после подтверждения.
- Интерактивное меню, планы без применения, таймауты команд, запрет параллельных запусков, проверка записи настроек, автоматическая попытка отката при ошибке применения.
- Никаких загрузок кода, телеметрии, автозапуска и внешних Python/Node-зависимостей на телефоне.

### Чего здесь намеренно нет

Удаления/отключения пакетов, `pm clear`, убийства всех приложений, «освобождения ОЗУ», сброса статистики батареи, принудительного Doze, отключения термозащиты, изменения частот/напряжений CPU/GPU, сетевых «твиков» и массовой компиляции приложений. Такие действия могут повредить стабильности, уведомлениям, автономности или просто ухудшить производительность.

## Необязательно: полный режим через Shizuku

**Для базового запуска этот раздел не нужен.** Следуйте ему только если нужны shell-проверки и системные изменения. При установке через git шаг распаковки ZIP пропустите.

### 1. Подготовьте Shizuku

Используйте официальные проекты:

- [Shizuku](https://github.com/RikkaApps/Shizuku)
- [Termux](https://github.com/termux/termux-app)

На Android 11+ Shizuku обычно запускается без root через **беспроводную отладку**: включите параметры разработчика, включите беспроводную отладку, выполните сопряжение по инструкции Shizuku и нажмите «Запустить». На Android 6–10 обычно нужен запуск Shizuku с компьютера через ADB. Возможности зависят от прошивки; выполняйте подсказки установленной версии Shizuku.

После перезагрузки телефона Shizuku, как правило, нужно запускать заново. Сам скрипт не включает отладку, не выполняет сопряжение и не может сам себе выдать разрешения.

### 2. Распакуйте файлы в домашний каталог Termux

Скачайте подготовленный `Android-Care.zip` из ответа или ZIP исходников репозитория. Распакуйте **все файлы**, а не только `run.sh`.

Для архива из ответа, сохранённого в «Загрузки»:

```sh
# В Termux: разрешите доступ к общему хранилищу по запросу Android.
termux-setup-storage
# При необходимости установите unzip штатным пакетным менеджером Termux:
pkg install unzip
unzip "$HOME/storage/downloads/Android-Care.zip" -d "$HOME"
cd "$HOME/Android-Care"
mkdir -p rish
```

Имя файла в «Загрузках» может отличаться — подставьте фактическое. У ZIP исходников GitHub будет другое имя корневой папки.

### 3. Экспортируйте rish из Shizuku

В Shizuku откройте **«Использование в терминальных приложениях»** (название может немного отличаться) и экспортируйте `rish` и `rish_shizuku.dex`. Это компоненты **вашей установленной версии** Shizuku; в репозитории их нет.

Скопируйте оба файла в `$HOME/Android-Care/rish/`. Например, если экспортировали прямо в «Загрузки»:

```sh
cp "$HOME/storage/downloads/rish" ./rish/
cp "$HOME/storage/downloads/rish_shizuku.dex" ./rish/
```

В экспортированном файле `rish` укажите пакет терминала по инструкции Shizuku: для обычного Termux это `com.termux` (вместо `PKG`, если такой маркер присутствует). У форков пакет может быть другим. На новых Android DEX должен быть недоступен для записи; если это требуется экспортированной версией, выполните:

```sh
chmod 400 ./rish/rish_shizuku.dex
```

Держите файлы в приватном `$HOME` Termux, не запускайте DEX из общей папки Downloads. Для замены read-only DEX при обновлении сначала верните право записи: `chmod 600 ./rish/rish_shizuku.dex`.

Проверьте доступ:

```sh
sh ./rish/rish -c 'id'
```

Разрешите терминалу доступ в диалоге Shizuku. Ожидается `uid=2000(shell)`; при root-бэкенде может быть `uid=0(root)`, но root не требуется. Пока эта проверка не работает, полный режим недоступен, но базовая диагностика работает без него.

### 4. Запустите проверку

```sh
sh run.sh
```

Без аргументов запускается **только диагностика**. Во время неё настройки не меняются; создаются локальные отчёт и служебные временные файлы. На медленном телефоне проверка может занять несколько минут: у тяжёлых разделов отдельные лимиты времени.

Меню всех действий:

```sh
sh run.sh menu
```

Если rish уже установлен в другом месте:

```sh
RISH="$HOME/путь/rish" sh run.sh menu
```

`run.sh` передаёт текст скрипта удалённой оболочке через `rish -c`, а не пытается открыть приватный файл Termux от имени shell. Поэтому меню и подтверждения сохраняют доступ к вводу. Передача аргументов не использует `eval`.

## Команды

| Команда в Termux | Действие |
| --- | --- |
| `sh run.sh` или `sh run.sh audit` | Отчёт без изменения настроек |
| `sh run.sh menu` | Интерактивное меню |
| `sh run.sh optimize` | Показать план, ничего не применять |
| `sh run.sh optimize --apply` | После ввода `ДА` сохранить исходные значения и ограничить анимации сверху значением 0.5x |
| `sh run.sh restore` | Показать сохранённые значения, без записи |
| `sh run.sh restore --apply` | После ввода `ДА` восстановить сохранённые анимации |
| `sh run.sh trim` | Объяснить очистку, ничего не удалять |
| `sh run.sh trim --apply` | После ввода `ДА` запросить системную очистку кэша |
| `sh run.sh game com.example.game` | Прочитать режимы и существующие конфигурации выбранной игры |
| `sh run.sh frames com.example.game` | Сводка накопленной HWUI-статистики, не FPS игры |
| `sh run.sh monitor` или `sh run.sh monitor 12` | CSV-серия: по умолчанию 6 отсчётов, максимум 12 |
| `sh run.sh game-boost com.example.game` | Показать план, без изменений |
| `sh run.sh game-boost com.example.game --apply` | Подтверждаемый выбор уже поддерживаемого performance после проверки температуры |
| `sh run.sh game-restore` / `sh run.sh game-restore --apply` | Просмотр / подтверждаемый откат игрового режима |
| `sh run.sh help` | Справка (доступна даже без Shizuku) |

В базовом режиме все системные изменения и запросы игровых/HWUI-данных заблокированы, в том числе из меню. Работают диагностика, просмотр плана и мониторинг доступных без shell величин.

`com.example.game` — пример, подставьте точное имя пакета своей игры; скрипт не выбирает игры и не сканирует личные приложения автоматически.

`--apply` **не заменяет** подтверждение. Любой ответ кроме точного `ДА`, включая отсутствие ввода, отменяет действие. Флага обхода подтверждения нет.

### Анимации и откат

Меняются только три ключа в `settings global`:

```text
window_animation_scale
transition_animation_scale
animator_duration_scale
```

Это влияет на ощущение скорости переходов, **не повышает FPS и мощность CPU/GPU**. Уже выключенные анимации (0) и значения быстрее 0.5x сохраняются: оптимизация никогда не увеличивает их длительность. На некоторых оболочках действие ограничено производителем. Это глобальные настройки: учитывайте других пользователей устройства.

Снимок хранится в `/data/local/tmp/android-care/animations.tsv`. Повторное применение не перезаписывает его: сначала выполните откат. Файл читается как проверенные данные, не как исполняемый shell-код. Если измените эти настройки вручную после применения, `restore` всё равно вернёт значения **из снимка**, а не последние ручные изменения.

При ошибке записи скрипт проверяет результат и пытается восстановить все три исходных значения. При прерывании процесса или неудачном откате снимок остаётся — запустите `restore --apply` снова. При выключении питания, SIGKILL или очистке `/data/local/tmp` абсолютная гарантия восстановления невозможна. Не удаляйте снимок, пока нужен откат; при необходимости сохраните его вне телефона.

### Игровой performance: что именно происходит

Это **не универсальная разблокировка FPS**. Команда выбирает штатный режим Android для конкретной игры, если его уже разрешили система и приложение. Не создаются `device_config` overrides, не задаётся произвольный FPS, не подменяется модель телефона. Но **сам существующий режим может включать настроенные производителем/игрой FPS-ограничения и масштабирование**. Сначала посмотрите `game PACKAGE`, затем сравнивайте одинаковые игровые сценарии.

Перед применением нужны:

1. Shell-доступ и совместимый ответ `cmd game list-modes PACKAGE`; текущий пользователь должен оставаться тем же после подтверждения.
2. Поддерживаемый `performance`, а не принудительная запись неизвестного режима. Уже выбранный performance повторно не применяется.
3. Доступный, не подменённый `Thermal Status` с готовым HAL и статусом 0/1. При 2 и выше или неизвестном/OEM-формате запись отклоняется.
4. Достоверная температура батареи ниже **40 °C**, без симуляции `UPDATES STOPPED`. Это осторожная политика скрипта, **не универсальная граница опасной температуры** производителя.
5. Ввод `ДА` и успешное сохранение исходного режима в `/data/local/tmp/android-care/game.tsv`.

После записи режим перечитывается. При ошибке выполняется попытка отката; при прерывании/неполном откате снимок остаётся. Для повторного восстановления — `game-restore --apply`, находясь в **том же Android-пользователе**. В снимке одна игра; он не затирается повторным boost. Восстанавливается только выбор режима, не чужие параллельные изменения конфигураций. Снимок анимаций независим.

Game Manager появился в новых Android, но состав shell-команд отличается между версиями и OEM. Если `list-modes` отсутствует или имеет неизвестный формат, скрипт отказывается от записи даже на новом Android. Отказ — ожидаемое поведение, а не повод обходить защиту.

**Performance может увеличить расход и нагрев и не гарантирует прироста.** Проверка температуры выполняется до записи: после завершения нет фонового наблюдения и автоматического возврата режима при последующем нагреве. Системная термозащита не отключается.

### Как искать просадки, а не «рисовать FPS»

```sh
# Сначала воспроизведите один и тот же игровой сценарий:
sh run.sh game com.example.game
sh run.sh frames com.example.game
# Наблюдение во времени без искусственного стресс-теста:
sh run.sh monitor 12
```

`frames` — **накопленные HWUI** total/jank/p50/p90/p95/p99 и GPU-процентили. Они могут описывать меню и не покрывать игровой SurfaceView/OpenGL/Vulkan. Нет кадров — нет измерения, а не «0 FPS». Счётчики не сбрасываются, приложение не убивается/перезапускается; результаты разных окон нельзя прямо сравнивать как одинаковый бенчмарк. Для реального игрового FPS нужен подходящий счётчик игры или трассировка, покрывающая её рендер.

`monitor` сохраняет CSV с timestamp, aggregate CPU busy %, MemAvailable в kB, батареей в °C и thermal status 0–6. Первый CPU-отсчёт — `NA` (нет предыдущего), недоступные показатели тоже `NA`. Между отсчётами пауза 5 с **плюс время чтения датчиков**: 12 отсчётов — не обещание ровно минуты. CPU считается по разнице `/proc/stat` по всем ядрам, не по процессу игры; короткие пики могут быть пропущены. Команда ничего не ускоряет и сама добавляет небольшую нагрузку. Android может ограничить Termux в фоне.

Сравнивайте несколько одинаковых прогонов с сопоставимыми температурой, зарядом, графикой и частотой экрана. Не сравнивайте холодный процесс с уже прогретым. Причину сложных просадок исследуют с Perfetto, а не через `1000 / p95` или частоту дисплея. Скрипт не записывает тяжёлую системную трассу автоматически.

### Очистка кэша

Запускается только явным действием `trim --apply` / пунктом меню. Команда: `pm trim-caches 1G internal`.

**1 GiB — цель свободного места, а не обещанный объём удаления.** Если свободного места уже достаточно, Android может ничего не удалить. Это не полная очистка всех кэшей и не исправление файловой системы. Android сам выбирает доступный восстанавливаемый кэш приложений. Личные данные и настройки приложений не сбрасываются; кэш, в том числе временно загруженный контент, может потребоваться скачать заново. Первый запуск приложений может стать медленнее. **Отката удаления кэша нет.**

Лимит ожидания — 120 секунд. При таймауте часть кэша уже могла быть удалена; не считайте операцию атомарной и не запускайте её циклически.

## Отчёты и приватность

Отчёты полного режима: `/data/local/tmp/android-care/`; базового режима: `$HOME/.android-care/`. Файлы общей проверки — `report-*`, игры — `game-report-*`, HWUI — `frames-report-*`, мониторинга — `monitor-*` в Termux (обычные UTF-8 текстовые файлы без расширения). Базовый отчёт можно читать обычным `cat "$HOME/.android-care/report-ИМЯ"` без rish. Путь выводится в конце проверки. Каталог имеет права 700, отчёты — 600. Обычный файловый менеджер без shell-доступа, скорее всего, не сможет их открыть.

Прочитать отчёт через rish, подставив его фактическое имя:

```sh
sh ./rish/rish -c 'cat /data/local/tmp/android-care/report-ИМЯ'
```

Сохранить копию в приватном каталоге Termux:

```sh
sh ./rish/rish -c 'cat /data/local/tmp/android-care/report-ИМЯ' > "$HOME/android-care-report.txt"
```

Скрипт не читает аккаунты, IMEI/серийный номер, переписки, список Wi-Fi, logcat или содержимое приложений. В общей проверке пакеты выводятся только количеством; в явных командах `game`, `frames`, `game-boost` отчёт/снимок содержит имя выбранного вами пакета и, для Game Mode, номер Android-пользователя. Сырые системные `dumpsys` могут содержать дополнительные метаданные, включая сведения о системных компонентах. Просмотрите отчёт перед публикацией. Ничего никуда не отправляется, отчёты автоматически не удаляются. Приложения с shell/root-доступом тоже могут их прочитать.

У отдельных разделов лимит вывода 100 строк. `Permission Denial`, отсутствие PSI/датчика, сервисов `thermalservice` или `diskstats` на старой/закрытой прошивке — **недоступная проверка, не диагноз поломки**. Код завершения диагностики 0 означает, что проход завершён, а не что всё оборудование исправно. Причины разряда требуют наблюдения во времени, а ёмкость/здоровье батареи нельзя надёжно измерить этим скриптом.

## Без Shizuku: ADB с компьютера

Используется тот же скрипт; shell-доступ даёт авторизованный ADB:

```sh
adb push scripts/android-care.sh /data/local/tmp/android-care.sh
adb shell sh /data/local/tmp/android-care.sh audit
# Для интерактивного меню / подтверждений нужен терминал:
adb shell -t sh /data/local/tmp/android-care.sh menu
```

Root не нужен. Базовые проверки рассчитаны на Android API 23+ с системным `timeout`, но доступность команд отличается по прошивкам. Shizuku/rish, Termux и конкретная версия Android могут предъявлять более высокие требования.

## Если что-то не работает

- **Базовый режим / UID приложения вместо 2000/0:** это нормальная работа без повышенных прав. Если нужен полный режим, запустите Shizuku, настройте rish и проверьте разрешение терминала. Само наличие приложения Shizuku без rish не предоставляет терминалу shell-доступ.
- **Shizuku не работает после перезагрузки:** заново запустите службу и проверьте `sh ./rish/rish -c 'id'`.
- **Ошибка DEX / Permission denied:** проверьте инструкцию экспортированного rish, пакет терминала, расположение обоих файлов в приватном каталоге и read-only DEX. Не отключайте SELinux.
- **Снимок уже существует:** сначала `sh run.sh restore --apply`. Не удаляйте его ради повторного применения.
- **Снимок повреждён:** скрипт откажется менять настройки. Восстановите сохранённую копию или задайте нужные анимации вручную в параметрах разработчика. Не подставляйте неизвестные значения автоматически.
- **Старый lock:** сначала убедитесь, что другой запуск завершён (например, после перезагрузки телефона), затем удалите **только пустой каталог блокировки**:

  ```sh
  sh ./rish/rish -c 'rmdir /data/local/tmp/android-care/lock'
  ```

  В базовом режиме вместо этого: `rmdir "$HOME/.android-care/lock"`.

  Не делайте это во время работы скрипта. Не удаляйте весь каталог состояния — потеряете снимок отката.

- **Температуры или CPU недоступны:** это ограничение прошивки; root и обход защиты не требуются и не предлагаются.
- **Анимации снова изменились после перезагрузки:** прошивка или другое приложение могло перезаписать их. Скрипт не оставляет службу для принудительного удержания настроек.

## Проверка кода

На компьютере, Python 3.9+:

```sh
sh -n run.sh
sh -n scripts/android-care.sh
shellcheck -s sh run.sh scripts/android-care.sh
python3 -m unittest discover -s tests -v
```

CI выполняет те же проверки. Тесты имитируют Android-команды и проверяют отсутствие изменений при диагностике/просмотре плана, подтверждения, проверку UID, сохранение/откат исходных значений, запрет замедления уже выключенных/быстрых анимаций, ошибки записи, повреждённые снимки, блокировку, очистку кэша и передачу ввода через launcher, базовый режим без вызова привилегированных служб, блокировку всех изменений без shell, выбор режима, отказ rish и фильтрацию идентификаторов дисплея. Дополнительно проверяются игровые режимы/откаты/отказы и смена пользователя, тепловые ограничения и симулированные датчики, некорректные package names, пустая HWUI-выборка, формат и ограничения CSV-мониторинга.

**Физическое Android-устройство в этой среде не подключено.** Успех mock-тестов не доказывает совместимость со всеми прошивками. Начните на телефоне с `audit`, изучите отчёт и только затем подтверждайте нужные изменения.
